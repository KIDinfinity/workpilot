# 0003. 检索配置：分块 600/100 + dense + top_k=5（不启用 hybrid）

- 状态：已采纳
- 日期：2026-10-27

## 背景（要解决什么问题，有什么约束）

W5 的 RAG 检索链路此前是「写死在代码/默认值里」的一组参数：`chunk_size=600`、
`chunk_overlap=100`、`top_k=5`、纯向量（dense）检索。这些数字来自 Day16 的
一次性选型，没有留可复现的实验证据，也没人能回答「换成 1000 会更好吗」「加 BM25
混合检索能不能救一下 API 名/配置键这类精确词查询」。

约束：

- 语料是本地 `data/corpus`（FastAPI / React / Vite / 项目内部文档），中文问答为主。
- Embedding 固定 `bge-m3`（1024 维，Ollama 本地），不走外部托管。
- 评测集 `eval/datasets/kb_qa.jsonl` 共 50 题：30 题库内、20 题库外。
- 一次完整评测（含生成）约 ¥0.04–0.08，实验次数必须可控。
- 参数必须能从外部切换（配置文件 / CLI），否则做不了 A/B。

## 决策（选了什么）

**保留默认分块 `chunk_size=600` / `chunk_overlap=100`，检索模式 `dense`，
`top_k=5`；同时把四个参数全部外置为可配置项**（`CHUNK_SIZE`、`CHUNK_OVERLAP`、
`TOP_K`、`RETRIEVAL_MODE`），并给 ingest 与评测加 `--config <yaml>`：

- 优先级：**CLI > YAML > `.env`/settings**。
- 每个实验写独立 collection（`kb_exp_<name>`），不覆盖线上 `kb_default`；
  重建时 manifest 记录 `chunk_size / overlap / chunks / retrieval`。
- `RETRIEVAL_MODE` 支持 `dense | hybrid`，hybrid 用 Qdrant 命名向量
  （`dense` + sparse `bm25`）配合 `prefetch` + `FusionQuery(RRF)`，代码保留可用，
  但**默认不启用**。

数据（`eval/reports/20261027-*`，50 题，git `f10c970`）：

| 变体 | 配置 | chunks | hit@1 | hit@5 | MRR | 误拒率 | 检索P95 |
|---|---|---|---|---|---|---|---|
| c300_o0 | 300/0/top5/dense | 1737 | 0.737 | 0.895 | 0.792 | - | 85ms |
| c300_o100 | 300/100/top5/dense | 2221 | 0.737 | 0.868 | 0.790 | - | 88ms |
| **c600_o100** | **600/100/top5/dense** | **1077** | **0.737** | **0.921** | **0.789** | **0.132** | **90ms** |
| c600_o0 | 600/0/top5/dense | 994 | 0.737 | 0.921 | 0.793 | - | 81ms |
| c1000_o0 | 1000/0/top5/dense | 736 | 0.737 | 0.921 | 0.802 | 0.158 | 84ms |
| c1000_o100 | 1000/100/top5/dense | 756 | 0.737 | 0.921 | 0.800 | - | 92ms |
| hybrid c600_o100 | 600/100/top5/hybrid | 1077 | 0.605 | 0.816 | 0.715 | - | 112ms |
| hybrid c1000_o0 | 1000/0/top5/hybrid | 736 | 0.605 | 0.816 | 0.719 | - | 105ms |

top_k（均 `--with-answer`，成本含生成侧）：

| 变体 | 误拒率 | 回答P95 | 成本 |
|---|---|---|---|
| c1000_o0-k3 | 0.211 | 2175ms | ¥0.0541 |
| c1000_o0-k5 | 0.158 | 2103ms | ¥0.0538 |
| c1000_o0-k8 | 0.158 | 2131ms | ¥0.0766（+42%） |
| **c600_o100-k5** | **0.132** | **2215ms** | **¥0.0407** |

判定逻辑：

1. **hit@5 是硬门槛** —— c600_o100 与 c1000_o0 同为 0.921，无差别。
2. 二者 MRR 差 0.013（0.789 vs 0.802），小于一个名次位；而 c1000_o0 的库内误拒率
   0.158 明显高于 c600_o100 的 0.132（长 chunk 稀释了 top1 相似度），生成侧成本也
   高 24%（¥0.0538 vs ¥0.0407）。**误拒比 MRR 更伤用户体验**（明明库里有却拒答），
   故取 c600_o100。
3. top_k：k=3 误拒 0.211 不可接受；k=8 与 k=5 误拒相同（0.158/0.132）却贵 42%，
   故 k=5。
4. **hybrid 落选**：两套分块下 hit@5 一律从 0.921 掉到 0.816、hit@1 从 0.737 掉到
   0.605，MRR 掉 ~0.085。按 tags 拆解，掉分集中在最该被 BM25 救的场景：

   | tag | n | dense hit@5 | hybrid hit@5 | dense MRR | hybrid MRR |
   |---|---|---|---|---|---|
   | fastapi | 7 | 1.000 | 0.714 | 0.719 | 0.449 |
   | llm_seed | 18 | 0.944 | 0.833 | 0.835 | 0.737 |
   | standard | 4 | 0.500 | 0.250 | 0.340 | 0.278 |

   具体掉出 top5 的题：q005（环境变量新增规则，tags 含 config）dense #4 → 未命中；
   q032（Swagger/Redoc 文档页，fastapi+openapi）#3 → #6；q033（Pydantic 请求体包一层
   键名，fastapi）#5 → #7。**反向变好的一题都没有。**

原因判断：fastembed 的 `Qdrant/bm25` 是英文分词 + 小写 + 英文停用词，对中文 query
几乎切不出有意义的 token，sparse 通道本身召回质量差；此时 RRF 融合把 dense 的强
排序与噪声按名次等权相加，等于主动稀释了原本正确的 top1。中文场景要做混合检索，
需要换中文分词的 sparse 编码器（如 `bm25` 前置 jieba / `bge-m3` 自带 sparse 输出），
并把融合从 RRF 换成带权重的分数归一化。

## 备选方案（列出并说明放弃理由）

- **c1000_o0（MRR 最高 0.802）**：hit@5 与 c600_o100 持平，但误拒率高 2.6pp、
  生成成本高 24%；MRR 优势在一个名次位内，不足以补偿。作为「若后续补难题集后
  MRR 权重上升」的备选保留（只需改 `CHUNK_SIZE=1000` + `CHUNK_OVERLAP=0` 重建）。
- **c300_o0 / c300_o100**：chunks 数量翻倍到 1737/2221，hit@5 反而掉到
  0.895/0.868（语义碎片化，单 chunk 讲不完一个概念），存储与 embedding 成本也翻倍，
  直接否决。
- **hybrid（dense + BM25 + RRF）**：见上，全指标劣化且无单题收益，代码保留但默认关闭。
- **引入 rerank 模型（bge-reranker 等）**：能同时提 MRR 和压误拒，但要多一个模型
  服务与一次前向延迟，不在 W5 范围；已记入 W6 候选。
- **改 `score_threshold` 硬截断**：Qdrant 分数分布随分块变化，阈值不可跨配置复用，
  且 hybrid 下 RRF 分数与余弦不可比；不采用静态阈值。

## 后果（好处 / 代价 / 后续动作）

好处：

- 四个参数从代码常量变成配置项，任何一次分块/检索实验都能用
  `--config eval/configs/<name>.yaml` 复现，且不污染 `kb_default`。
- 线上配置有实验数据背书（46 个 pytest 用例 + 8 组实验报告 + 1 次交叉验证）。
- 误拒率 0.132 是当前所有候选里最低的，问答可用性最好。

代价 / 已知不足：

- **评测集太简单**：6 个分块变体的 hit@1 完全一致（0.737），说明题目区分度不足，
  MRR 差异都在一个名次位量级内；本次结论的置信度受此限制。→ W5 Day21 补难题
  （多跳、需要精确 API 名、跨文档对比）。
- hybrid 通道虽可用但当前实现（英文 BM25 + RRF）对中文无效，属于「有代码无收益」，
  需在 W6 重做分词/融合后才值得再评估。
- `c600_o100` 的 MRR 0.789 与基线一致，说明本次改动**没有让线上变好**，价值在于
  「参数可配置 + 决策有据 + 排除 hybrid」，而非指标提升。

后续动作：

1. `.env` 固化 `CHUNK_SIZE=600 / CHUNK_OVERLAP=100 / TOP_K=5 / RETRIEVAL_MODE=dense`，
   按此重建 `kb_default` 并核对点数（1077）。
2. Day21 扩题集；若难题集上 MRR 权重上升，重跑 c1000_o0 对比。
3. W6 评估 rerank（bge-reranker-base）与中文分词 BM25。
