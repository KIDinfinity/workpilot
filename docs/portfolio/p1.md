# P1 技术复盘：WorkPilot Knowledge（v0.5）

> 一句话：从零手写一个「带引用、会拒答、可评测」的研发知识 RAG 助手，用 50 题评测集 + LLM-as-a-judge 把检索质量、幻觉、成本量化到可追溯的数字。
>
> 时间：W2–W8（约 60–80 小时）｜仓库：<https://github.com/KIDinfinity/Infinity_AI_Project>｜Demo：[docs/assets/demo.gif](../assets/demo.gif)

---

## 1. 为什么需要 RAG？

- **问题**：研发知识（团队规范 / 技术决策 / 组件用法）分散在几十个 markdown 里，一次查找耗时 10–30 分钟，DA-01 定义里把这类「知识查找 + 上下文切换」的损失量化为 **每周 115 分钟**，目标节省 ≥ 60%（[docs/product/da01-definition.md](../product/da01-definition.md)）。
- **为什么不是微调**：知识每周在变（新规范、新 ADR），微调一次要重训、要数据标注，跟不上节奏；且微调后模型仍无法给出「答案来自哪一段」。
- **为什么不是长上下文**：把全部文档塞进 prompt，token 成本随语料线性涨，且没有检索隔离，反而容易「引用错文档」。
- **RAG 的取舍**：检索先行缩小范围 → 只把 top-k 片段喂给模型 → 答案天然带可溯源引用。代价是要自己维护「切分 / 索引 / 检索 / 评测」一整条链路。
- 证据：[docs/adr/0004-handwritten-rag.md](../adr/0004-handwritten-rag.md)、[docs/product/da01-definition.md](../product/da01-definition.md)。

## 2. 为什么使用 Qdrant？

- **结论**：选 Qdrant 单容器，因为「payload 过滤 + 命名向量 hybrid + snapshot 快照」三样能力都在，且运维足够轻。
- **payload 过滤**：每个向量带 `doc_id` / `title` / `section`，检索时按 doc 过滤，是「按文档溯源引用」和「删除单个文档」的前提（删除 = 按 `doc_id` 过滤删除，见 [apps/api/app/rag/retrieve.py](../../apps/api/app/rag/retrieve.py)）。
- **hybrid**：命名向量（dense bge-m3 + sparse BM25）+ `FusionQuery(RRF)`，代码保留、默认 dense（[docs/adr/0003-chunking-retrieval.md](../adr/0003-chunking-retrieval.md)）。
- **快照恢复**：用 collection snapshot 做备份，实测 **RTO = 1 分钟（22 秒）**（[docs/runbook.md](../runbook.md)、[deploy/scripts/backup.sh](../../deploy/scripts/backup.sh)）。
- 放弃 pgvector（W4 时还没有 Postgres）、Milvus（分布式过重）、Chroma（快照/过滤/混合能力弱），见 [docs/adr/0002-qdrant.md](../adr/0002-qdrant.md)。

## 3. Chunk 如何设计？

- **结论**：**按标题结构切分 + 定长兜底**，最终配置 **chunk_size=600 / overlap=100 / dense / top_k=5**（[docs/adr/0003-chunking-retrieval.md](../adr/0003-chunking-retrieval.md)）。
- 标题结构切分保证一个 chunk 语义自洽（不把「问题」和「答案」切断）；定长兜底处理无标题的纯文本。
- **W5 Day20 分块实验**（[eval/reports/20261027-retrieval-experiments.md](../../eval/reports/20261027-retrieval-experiments.md)）：

| 变体 | chunks | hit@1 | hit@5 | MRR |
| --- | ---: | ---: | ---: | ---: |
| c300_o0 / c300_o100 | 1737 / 2221 | 0.737 | 0.895 / 0.868 | 0.792 / 0.790 |
| c600_o0 / c600_o100 | 994 / 1077 | 0.737 | **0.921** / **0.921** | 0.793 / 0.789 |
| c1000_o0 / c1000_o100 | 736 / 756 | 0.737 | **0.921** / **0.921** | 0.802 / 0.800 |

- 关键结论：c300 切太碎、hit@5 掉到 0.868–0.895（语义碎片化，否决）；c600 与 c1000 的 hit@5 并列 0.921，但 c600_o100 的**库内误拒率更低（0.132 vs 0.158）、生成成本更低（¥0.0407 vs ¥0.0538，-24%）**，故取 c600_o100。

## 4. Retrieval 如何评估？

- **结论**：用 **50 题评测集（库内 30 / 库外 20）**，测 `hit@k`、`MRR`、**引用正确率**，再叠加 **LLM-as-a-judge**（正确性 / 忠实度）。
- 库外题单独测「拒答正确率」，防止系统用「编造」蒙混过关——这是 RAG 可信度的核心指标。
- **基线 v0.2 → 当前 v0.3**（[eval/reports/20261023-rag-baseline.md](../../eval/reports/20261023-rag-baseline.md) / [eval/reports/20261028-rag-v0.3.md](../../eval/reports/20261028-rag-v0.3.md)）：

| 指标 | v0.2 | v0.3 | 目标 |
| --- | ---: | ---: | ---: |
| hit@5 | 0.921 | 0.921 | ≥ 0.85 |
| 引用正确率 | 待测 | 1.000 | ≥ 0.80 |
| 库外拒答正确率 | 1.000 | 1.000 | ≥ 0.80 |
| 库内误拒率 | 0.132 | 0.053 | — |
| 正确性均值 (judge) | — | 0.85 | — |
| 忠实度 (judge) | — | 1.0 | — |
| P95 延迟 | 2280 ms | 2708 ms | < 8 s |

- 评测是可复现的：`eval/datasets/kb_qa.jsonl` + `eval/runners/*`，每次报告带 git sha（[eval/reports/](../../eval/reports/)）。

## 5. 有哪些 Badcase？

- **结论**：维护了 **12 条 badcase 库（BC-001~BC-012）**，根因分布（[eval/badcases/badcases.md](../../eval/badcases/badcases.md)）：

| 根因 | 数量 | 代表 |
| --- | ---: | --- |
| 召回排序靠后 | 3 | BC-001、BC-003、BC-012 |
| 数据缺失（语料没入库） | 5 | BC-002、BC-005、BC-006、BC-007、BC-008 |
| 生成幻觉 / 引用错误 | 1 | BC-011 |
| 过度拒答 | 1 | BC-010 |

- **案例 1 · 过度拒答（v0.3 主修）**：首轮 14 条 `correctness ≤ 1` 里「过度拒答」占 7 条。根因是 `SCORE_THRESHOLD=0.60` 太严。把阈值从 0.60 调到 **0.52**，并让 `qa_answer.v2` 鼓励「证据不足时回答有依据的部分」，**库内误拒率 0.184 → 0.053**（[eval/reports/20261028-rag-v0.3.md](../../eval/reports/20261028-rag-v0.3.md)）。
- **案例 2 · 生成幻觉 BC-011**：问「后端新增环境变量的规则」，答案正确引用了规范 §4，却把 Vite 前端语义（`import.meta.env` 加载优先级）拼进后端结论。根因是「环境变量」一词在前后端语境里召回混叠。修复思路：在 prompt 里区分前后端 env 边界（记为 W5 待办）。
- 教训：badcase 必须带「现象 → 定位（检索 / 生成 / 语料）→ 修复 → 回归数字」四要素，否则无法判断修没修好。

## 6. 如何降低幻觉？

- **结论**：四层防线，把「编造」压到可测量，实测**引用正确率 1.000、库外拒答正确率 1.000**（[eval/reports/20261028-rag-v0.3.md](../../eval/reports/20261028-rag-v0.3.md)）。
  1. **检索隔离**：只把 top-k 命中的片段喂给模型，模型没有「自由发挥」的语料来源。
  2. **引用约束 prompt**：`qa_answer.v2` 明确「只基于给定片段作答，逐句标注 `[n]`」，禁止引入片段外信息（[apps/api/app/llm/prompts/qa_answer.v2.md](../../apps/api/app/llm/prompts/qa_answer.v2.md)）。
  3. **阈值拒答**：检索最高分低于 `SCORE_THRESHOLD` 时直接拒答（「知识库中没有找到相关内容」），库外拒答正确率 1.0。
  4. **引用编号校验**：生成后校验正文 `[n]` 与返回 citations 一一对应，编号越界 / 缺失即判错（引用正确率 1.0）。
- 诚实边界：无法 100% 消除幻觉——BC-011 就是「检索对了、生成错了」的残留案例，靠评测持续兜底而非宣称零幻觉。

## 7. 如何控制成本？

- **结论**：每次调用**精确计量**，实测**单次问答 ¥0.0020、50 题总成本 ¥0.10**（[eval/reports/20261028-rag-v0.3.md](../../eval/reports/20261028-rag-v0.3.md)）。
- **计量**：W3 引入 pricing，按 cache hit / miss / output 三段计价，`calc_cost()` 从 usage 精确算钱，不猜（[apps/api/app/llm/pricing.py](../../apps/api/app/llm/pricing.py)）。
- **embedding**：本机 Ollama bge-m3（dev）与 SiliconFlow 同模型（prod）可切换，检索侧成本可忽略（[docs/adr/0005-compose-caddy.md](../adr/0005-compose-caddy.md)）。
- **top_k 控制上下文**：top_k 实验显示 k=8 相比 k=5 成本 +42% 而误拒率无改善，故锁 k=5（[eval/reports/20261027-retrieval-experiments.md](../../eval/reports/20261027-retrieval-experiments.md)）。
- **月成本估算**：假设 5 人 × 每天 10 问 × 22 天 = 1100 问 × ¥0.0020 ≈ **¥2.2 / 月**，远低于目标单次 < ¥0.02 的预算线。

## 8. 如何部署？

- **结论**：**单机 Docker Compose + Caddy 反代**，2C4G 一台云主机跑 web / api / qdrant / minio 四个容器（[docs/adr/0005-compose-caddy.md](../adr/0005-compose-caddy.md)、[deploy/docker-compose.prod.yml](../../deploy/docker-compose.prod.yml)）。
- **SSE 流式**：Caddy `reverse_proxy { flush_interval -1 }` 关闭缓冲，逐 token 下发，否则流式问答退化成一次性返回。
- **可观测**：`request_id` 贯穿日志、`/health` + `/ready` 健康检查、CI 跑测试（[apps/api/app/routes/health.py](../../apps/api/app/routes/health.py)）。
- **备份 / 恢复**：Qdrant snapshot + MinIO 备份脚本，实测 **RTO = 1 分钟（22 秒）**（[docs/runbook.md](../runbook.md)）。
- 当前 HTTP 明文 + basic_auth，仅作 Demo 门禁；域名 / TLS 是「加一行 Caddyfile 站点地址」即可启用的后续优化项。

## 反思

- **做得好**：
  - 每个数字都可追溯到评测报告 / ADR / 代码路径，复盘不靠记忆。
  - 评测集区分「库内 / 库外 / 多跳」，把「拒答正确率」单独拎出来测，抓住了 RAG 可信度的本质。
  - badcase 库带根因分类 + 修复版本 + 回归数字，是持续改进的资产而非一次性清单。
- **做错 / 返工**：
  - 一开始没在向量 payload 里存 `doc_id`，导致「删除单个文档」无法实现，返工补了 payload 过滤（见 ADR 0002 的代价一节）。
  - 阈值一开始拍脑袋定 0.60，导致库内误拒率 0.184 偏高，靠回归才调到 0.52。
  - hybrid 检索（dense + BM25）在中文语料上整体变差（hit@5 0.921→0.816），因为 fastembed 的 BM25 是英文分词；验证成本花在了「证明它不行」上——但这是必要的证伪。
- **如果重做**：先把「引用正确率」和「库外拒答率」作为一等指标，再调召回；先定评测集，再动配置。
- **下一步（P2 / W9）**：把 `kb_search` 封装成 Agent 工具（MCP），让检索从「问答终点」变成「Agent 可调用的一环」。

## 3 分钟讲稿

大家好，我来讲一个自己从零写的项目：WorkPilot，一个带引用的研发知识 RAG 助手。

（问题）我在日常研发里反复卡在一件事上：团队规范、技术决策、组件用法散在几十个 markdown 里，查一次要 10 到 30 分钟，算下来每周浪费 115 分钟。通用大模型要么不知道这些内部知识，要么会一本正经地编。

（方案）所以 WorkPilot 做三件事：把文档切块入库，检索后用 top-k 片段让模型作答，答案逐句标注 `[n]` 引用；检索不到就明确拒答；用户点 👎 和原因，导出来变成评测 badcase。架构就是 web + FastAPI + Qdrant + 本地 embedding，单机 Compose 一键部署。

（关键设计）我坚持手写整条 RAG 链路而不是套框架，因为想清楚每一步在干什么。切分上做了 chunk 300/600/1000 的实验，600 最均衡，hit@5 到 0.921。检索上试过 dense+BM25 的 hybrid，中文场景反而掉到 0.816，所以保留 dense。降幻觉靠四层：检索隔离、引用约束 prompt、阈值拒答、引用编号校验。

（评测结果）我用 50 题评测集——库内 30、库外 20——去测。结果 hit@5 是 0.921，引用正确率 1.0，库外拒答正确率 1.0，单次成本两厘钱。关键是库内误拒率从 0.132 压到 0.053，因为我发现阈值太严会「该答不答」。

（工程化）前端流式输出，Caddy 关掉缓冲逐 token 下发；Docker 部署，备份恢复实测 RTO 一分钟。

（下一步）下一步把检索封装成 Agent 工具，让 WorkPilot 从「问答」变成「能调知识库的智能体」。谢谢。
